# GCSORT

**GCSORT** (formerly OCsort) is a free and open-source sort tool that implements a subset of the functionality of the Micro Focus (IP) MFSORT (c) utility.

*   **Main features:** SORT, MERGE, COPY, and JOIN.
*   **License:** Distributed under the GNU General Public License (see `COPYING` for details).

GCSORT is integrated with the GnuCOBOL compiler through the use of `libcob`. For file access (Sequential, Line sequential, Relative, and Indexed), it utilizes the native data access features available in libcob. The command formalism is compatible with DFSORT.

From the command line, thread management can be enabled to parallelize execution.

---

## 🏗️ Core Architecture & GnuCOBOL Integration

GCSORT introduces a dual-layer subsystem designed to handle sorting and merging operations both inside native COBOL application loops and standalone runtime environments.

### 1. EXTSM Module (In-Memory Bridge)
The **`EXTSM`** component acts as the high-level reference handler that intercepts native COBOL `SORT` and `MERGE` verbs via standard **FCD3** (File Control Description) interface blocks.
*   **Opcode Interception:** Resolves operational codes passed directly from the runtime: `0xFA01` (SORT Init), `0xFA40` (MERGE Init), `0xFAF3` (RELEASE), `0xFA10` (EOF), `0xFAF5` (RETURN), and `0xFA88` (CLEANUP).
*   **Metadata Parsing:** Automatically decodes Big-Endian native metadata out of the Key Descriptor Block (`KDB`) to register key properties and structures dynamically.
*   **File Binding:** Resolves file tables (`FDB`) to deduce layouts (Fixed vs Variable), maximum thresholds, and file organization modes.

### 2. LIBGCS Module (Core Sorting Engine)
The **`libgcs`** framework implements the low-level processing pipeline and memory management routines for GCSORT.
*   **Context Detection:** Features dynamic fallback checking (`gcs_check_cobol_runtime`). If a pure C container calls the library, it programmatically instantiates a headless runtime environment (`cob_init_nomain`) and creates a tracking mock context.
*   **Memory Pipelining:** Streams data records directly into highly optimized volatile storage grids (`gcs_LoadInMemory`).
*   **Disk Segmentation:** When the input volume overruns boundary gauges, the engine shifts records onto disk storage tracks via memory-mapped I/O operations, coordinating up to 16 synchronized temporary files (`Job_tmpfile_t`) for multi-way merge processing.

* EXTSM and libgcs are generated by the same makefile.
The build process also creates testlibgcs, which is an example of C language calls to the libgcs library. The creation of the testlibgcs executable is triggered by the main makefile, 
or the build can be initiated using the testlibgcs.mak file (makefile).
 
* extsmtst5
To test the EXTSM module, there is a COBOL file (extsmtst5) that calls the EXTSM component.
extsmtst5 accepts three parameters:
1) Number of input files (minimum 0, maximum 3); if zero, the data is generated by the COBOL program; otherwise, it reads from input files
2) Number of output files (minimum 0, maximum 1); if zero, the data is displayed on the screen
3) Type of operation (optional), which can be set to ‘MERGE’ to simulate the file merge phase.

## 🚀 Preload & Environment Configurations

To ensure the COBOL runtime redirects native operations to GCSORT correctly, configure your environment as follows:

### 🐧 Linux / UNIX Environment
```bash
export COB_PRELOAD="/opt/libs/libgcs.so:/opt/libs/EXTSM.so"
export LD_LIBRARY_PATH=".:$LD_LIBRARY_PATH"
export COB_LIBRARY_PATH=".:${COB_LIBRARY_PATH:+:$COB_LIBRARY_PATH}"
```

### 🪟 Windows Environment
```cmd
set COB_PRELOAD=C:\path\to\libraries\EXTSM.dll
set PATH=.;%PATH%
```

## 💡 Syntax & Commands Overview

*   **Case Insensitive** syntax.
*   **Return codes:** `0` (OK) - `4` (Warning) - `16` (Error).
*   **Usage with file parameters:** `gcsort <options> take filename`.
*   **Usage from command line:** `gcsort <options> <control statements>`.

### Options
*   `-fsign=[ASCII|EBCDIC]`: Define display sign representation.
*   `-fcolseq=[NATIVE|ASCII|EBCDIC]`: Collating sequence to use.
*   `-febcdic-table=<cconv-table>/<file>`: EBCDIC/ASCII translation table.
*   `-mt=<num>`: Number of threads to be used (or dynamic management).

### Key Control Statements
```text
 SORT | MERGE | COPY FIELDS Control statement for Sort, Merge, Copy file(s)
 USE                 Declare input file(s)
 GIVE                Declare output file
 [ SUM FIELDS ]      Sum fields for same record key, or eliminate duplicate keys
 [ RECORD     ]      Record control statement
 [ INCLUDE    ]      Select input records that respect include condition(s)
 [ OMIT       ]      Omit input records that respect omit condition(s)
 [ INREC      ]      Reformat input record Before sort, merge or copy operation
 [ OUTREC     ]      Reformat input record After sort, merge or copy operation
 [ OUTFIL     ]      Create one or more output files for sort, merge or copy
 [ OPTION     ]      Specifies options for control statements
```

## 🔗 JOIN Control Statement

The **JOIN** facility allows GCSORT to combine records from two input files (**F1** and **F2**) based on matching keys, simulating relational database join operations.

### Syntax Workflow
```text
 JOIN
    USE                 Declare input file F1
    USE                 Declare input file F2
    GIVE                Declare output file
    JOINKEYS FILES=F1   Declare keys and filtering constraints for file F1
    JOINKEYS FILES=F2   Declare keys and filtering constraints for file F2
    UNPAIRED            Declare join behavior (Left/Right/Full Outer or Inner Join)
    REFORMAT FIELDS     Declare the structure and fields of the combined output record
    [ INCLUDE | OMIT ]  Filter records after the join operation
    [ INREC ]           Reformat record structure before the join operation
    [ OUTFIL ]          Create multiple output files from the resulting join dataset
```

### Detailed Command Specifications

#### 1. File Declaration
```text
USE  {Filename}             [File F1 or F2]
     ORG {Org}
     RECORD [F,{RecordLen}] | [V,{MinLen},{MaxLen}]
            [KEY ({Pos},{Len},{KeyType})]
```

#### 2. Key Mapping & Sub-Filtering
```text
JOINKEYS FILES={F1|F2},FIELDS=[({Pos},{Len},{Order}, ...)] [,SORTED] [,STOPAFT={nn}]
         [, INCLUDE | , OMIT] [ COND=({Condition})[,FORMAT={FormatType}] ]
```
*   `SORTED`: Optimizes execution if the input file is already sorted by the specified keys.
*   `STOPAFT={nn}`: Limits processing to the first `nn` records of the input file.

#### 3. Join Types (`UNPAIRED`)
Controls how unmatched records from both sources are handled (Inner Join vs Outer Joins):
*   *Default (Omitted):* **Inner Join**. Only outputs records whose keys match in both F1 and F2.
*   `UNPAIRED` | `UNPAIRED,F1,F2`: **Full Outer Join**. Includes paired records plus unpaired records from both F1 and F2.
*   `UNPAIRED,F1`: **Left Outer Join**. Includes paired records plus unpaired records from F1.
*   `UNPAIRED,F2`: **Right Outer Join**. Includes paired records plus unpaired records from F2.
*   `UNPAIRED,ONLY` | `UNPAIRED,F1,F2,ONLY`: Outputs **only** unpaired records from both files.
*   `UNPAIRED,F1,ONLY`: Outputs unpaired records **exclusively** from F1.
*   `UNPAIRED,F2,ONLY`: Outputs unpaired records **exclusively** from F2.

#### 4. Output Formatting (`REFORMAT`)
Constructs the final layout of the joined record:
```text
REFORMAT FIELDS=({File}:{Pos},{Len},{?},{File}:{Pos},{Len}...) [,FILL=[C'constant' | X'hh']]
```
*   `{File}`: Specifies the source record (`F1` or `F2`).
*   `?`: Optional **1-byte indicator lookup**. Inserts a status character into the output record:
    *   `'B'` (Both): Key found in both F1 and F2.
    *   `'1'`: Key found in F1, but missing in F2.
    *   `'2'`: Key found in F2, but missing in F1.
*   `FILL`: Defines the padding byte (`C'`char`'` or `X'hh'`) used to fill blank areas when handling unpaired records with missing fields.

## ⚙️ Environment Variables Reference

*   `COB_VARSEQ_FORMAT`: Used natively by GnuCOBOL.
*   `GCSORT_DEBUG`: `0` = Disable debug info, `1` = Debug enabled, `2` = Parser diagnostics.
*   `GCSORT_MEMSIZE`: Memory Allocation in bytes (Default: `512000000` bytes).
*   `GCSORT_MLT`: Number of pages for cache MemoryMappedFile.
*   `GCSORT_PATHTMP`: Pathname for temporary disk files (Default: `TMPDIR` / `TMP` / `TEMP`).
*   `GCSORT_STATISTICS`: `0` = Minimal info, `1` = Summary, `2` = Details, `5` = Totals rec.
*   `GCSORT_TESTCMD`: `0` = Normal operations, `1` = Validate command line boundaries only (NO SORT).
