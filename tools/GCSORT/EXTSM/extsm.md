# EXTSM - In-Memory Sort/Merge Module (GCSORT)

The **EXTSM** module manages sorting (**SORT**) and merging (**MERGE**) operations directly in memory. 
It interfaces with the COBOL runtime (`libcob` / GnuCOBOL) through standard **FCD3** (File Control Description) data structures.

---

## 🚀 Environment Variables Configuration

To ensure the COBOL runtime preloads the libraries and redirects native I/O verbs correctly, configure your environment as follows:

### 🐧 Linux / UNIX Environment
```bash
export COB_PRELOAD=/opt/libs/libgcs.so:/opt/libs/EXTSM.so
export LD_LIBRARY_PATH=.:$LD_LIBRARY_PATH
export COB_LIBRARY_PATH=.:${COB_LIBRARY_PATH:+:$COB_LIBRARY_PATH}
```

### 🪟 Windows Environment
```cmd
set COB_PRELOAD=C:\path\to\libraries\EXTSM.dll
set PATH=.;%PATH%
```

---

To test the EXTSM module, there is a COBOL file (extsmtst5) that calls the EXTSM component.
extsmtst5 accepts three parameters:
1) Number of input files (minimum 0, maximum 3); if zero, the data is generated by the COBOL program; otherwise, it reads from input files
2) Number of output files (minimum 0, maximum 1); if zero, the data is displayed on the screen
3) Type of operation (optional), which can be set to ‘MERGE’ to simulate the file merge phase.


## ⚙️ Supported Operation Codes (Opcodes)

The entry point processes the following operation codes passed by the COBOL program:

| Opcode (Hex) | Internal Constant | Operation Description |
| :--- | :--- | :--- |
| `0xFA01` | `OP_SORT_EX_LE_INIT`    | Initializes the SORT session |
| `0xFA40` | `OP_SORT_MERGE`         | Initializes the MERGE session |
| `0xFAF3` | `OP_SORT_EX_LE_RELEASE` | Passes a single record to the buffer (`RELEASE`) |
| `0xFA10` | `OP_SORT_EX_LE_END`     | Signals End of Input (EOF) |
| `0xFAF5` | `OP_SORT_EX_LE_RETURN`  | Retrieves a sorted record from memory (`RETURN`) |
| `0xFA88` | `OP_SORT_EX_LE_CLEANUP` | Terminates session and releases allocated resources |

## 🛠️ API & Core Functions

### `EXTSM` (Main Entry Point)
```c
GCSORT_API int EXTSM(unsigned char* func, FCD3* fcdin);
```
The primary entry point called directly by the COBOL `CALL` statement. It verifies whether it is a valid sort operation, checks that `fnamePtr` is valid, and dispatches execution to the appropriate logic based 
on the opcode (`func`) while updating the `fcdin` status structure.

### Core Internal Functions (`GCSORT`)
* **`EXTSMGC_init(FCD3* fcd)`**: Allocates dynamic memory buffers (`szBuffRek`, `szBuffKey`) for records and keys, initializing the core job structures and setting the operation type.
* **`EXTSMGC_push_record(FCD3* fcd)`**: Submits a record to the memory buffer via `gcs_LoadInMemory`. If the memory allocation threshold (`nLim01` / `nLim02`) is reached and segmentation is enabled, it automatically executes the sorting core and flushes data to temporary disk swap files.
* **`EXTSMGC_pop_record(FCD3* fcd)`**: Returns a single sorted record at a time to the COBOL program via the `recPtr` pointer. It manages the underlying on-disk merge processing if temporary files were created.
* **`EXTSMGC_sort_core(FCD3* fcd)`**: Executes the physical sorting algorithm on the accumulated data using `gcs_sort_data`.
* **`EXTSMGC_cleanup(void)`**: Destroys job instances, handles temporary disk file cleanups, and frees all dynamically allocated heap memory (`szBuffRek`, `szBuffKey`).

## 📋 Key Field Data Type Mapping

The `utils_getExtsmFieldTypeName` function decodes COBOL key metadata bytes into compatible sorting engine format identifiers:

| Identifier | Detected COBOL Data Type |
| :---: | :--- |
| **`CH`** | Standard Alphanumeric (Bit 7 of Byte 1 not set) |
| **`FL`** | Floating Point (Bit 2 of Byte 1 set) |
| **`BI`** | Binary / COMP-X / COMP-5 (Unsigned Non-Display Numeric) |
| **`FI`** | Binary / COMP-5 (Signed Non-Display Numeric) |
| **`PD`** | Packed-Decimal / COMP-3 (Non-Display Numeric) |
| **`ZD`** | Zoned Decimal / Standard Numeric Display / Sign Trailing Included |
| **`CST`**| Sign Trailing Separate |
| **`CLO`**| Sign Leading Included |
| **`CSL`**| Sign Leading Separate |

## 🔍 Diagnostics & Debugging

A structural dump utility is available to trace the state of `FCD3` structures exchanged between the runtime and the engine:

```c
void dump_fcd_structure(const FCD3* fcd, const char* label);
```

By activating the `#define EXTSM_DEBUG` macro inside the header file, detailed runtime diagnostics will be printed to the console via standard I/O, including:
* File status keys (`fileStatus`), file organization (`fileOrg`), and current open modes.
* Record limits (current, minimum, and maximum record lengths).
* Physical file names and pointers for `USING` / `GIVING` file lists.
* Cross-platform 64-bit memory addresses, session IDs, relative keys, and big-endian pointer resolutions (`COB_BSWAP_64`).
